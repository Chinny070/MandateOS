- Contract bootstrap initializes one member at weight 1. That sole founder can propose and execute the narrow member-add bootstrap exception. Added members also receive weight 1; no weighted-vote editing method was found. For sensitive governance, both quorum and approval thresholds are 6,666 bps, and at least two active members are required. ## Budget controls

The committed ledger fixes the cumulative ceiling at `10 GEN = 10000000000000000000 wei`. It separately tracks actual fees, committed fee quotes, actual test-value transfers, committed test-value liabilities, unknown liabilities, and remaining budget. Unknown fee or transaction outcomes retain the full reserved quote/value and block retries. This is an operational control in the deployment scripts, not an onchain global cap; the dashboard or a separate wallet can submit transactions outside it, so signing must remain restricted to the approved run.

The first financial verification value ceiling is `0.01 GEN = 10000000000000000 wei`, separate from fees and subject to the total 10 GEN ceiling. This is a maximum, not a spend instruction. No financial test transfer is included in the deployment script. Each such transfer still needs a distinct explicit approval, actual fee quote, two-wallet governance, and a stop-condition review.

**Fee estimate now:** not available. No live price RPC or source-matched measured fee profile. No numeric fee estimate should be inferred from local tests or generic fees. A run cannot start until the profile and fresh fee estimates show enough budget under the 10 GEN ceiling.

## Security and protocol review

- The dashboard now forwards the GenLayerJS fee distribution and `messageAllocations` for each wallet write. The helper refuses to write when chain ID or fee data is absent. StudioNet's unsupported fee-policy method currently prevents every such write from reaching the wallet submission path. No child-message fee sufficiency result is known.
- Core and ProjectVault perform asynchronous finalized value messages with state/reservations updated before emission. Existing Direct Mode tests cover authorization, replay and accounting, but do not execute child transactions or prove failure/refund behavior. Unknown/failing children can keep reservations and value at risk; no retry or arbitrary admin recovery has been added.
- Evidence URL validation requires bounded HTTPS and rejects common local/IP forms. It cannot verify DNS resolution or the final destination after redirects. The comparative assessment binds exact fetched content digest and decision fields, and malformed/inconclusive evidence fails closed; changes between validators can prevent consensus. Redirect/DNS rebinding controls and live Equivalence Principle consensus remain unverified because the supported web API does not expose those guarantees in the reviewed path.
- No new contract accounting or administrator authorization defect was demonstrated in this preparation pass. This is source review plus local tests, not a formal third-party audit. EOA payouts remain unsuitable for production; recipient acknowledgment is only an attestation.
